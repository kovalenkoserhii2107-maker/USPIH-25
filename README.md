# ОСББ «Успіх-25» — вебзастосунок мешканця

Статичний застосунок на ванільному JavaScript (ES-модулі, без бандлера).
Хостинг: GitHub Pages. Бекенд: Firebase (Auth + Firestore + Storage).

## Структура

```
index.html          розмітка всіх екранів
style.css           єдина дизайн-система (усі кольори — у :root)
style-chat.css      стилі чату
firestore.rules     правила доступу до Firestore
storage.rules       правила доступу до файлів
firestore.indexes.json індекси Firestore
functions/          захищені серверні операції та синхронізація ДТЕК
js/
  firebase.js       ініціалізація Firebase + об'єкт сесії
  ui.js             утиліти: екранування, формати, панелі, сповіщення
  attachments.js    типи файлів, галерея, переглядач документів
  owners.js         співвласники (атомарне збереження)
  power.js          статус електропостачання
  messages.js       розсилка та вхідні оголошення
  requests.js       звернення мешканців + база документів ОСББ
  polls.js          опитування (створення, голосування, підсумки)
  meetings.js       вкладка «Збори»: створення, активні, архів, протоколи
  meeting.js        розрахунки зборів: кворум, підсумки питань (без DOM)
  meeting_actions.js завершення зборів і публікація протоколів через Firestore
  paper_votes.js    внесення голосів, зібраних на папері під час обходу
  protocol_pdf.js   листки письмового опитування і протокол зборів (pdfmake)
  protocol_form.js  дані, які дописуються в протокол перед формуванням
  app.js            точка входу: вхід, маршрутизація, навігація
```

## Загальні збори співвласників

Збори — це запис у колекції `polls` з `isMeeting: true`. У полі `options`
лежить не список варіантів відповіді, а **порядок денний**; першим питанням
код завжди додає «Обрання голови та секретаря зборів». Відповіді на кожне
питання фіксовані: «За», «Проти», «Утримався».

Електронний або старий голос квартири — документ `polls/{id}/votes/{apt}`:

```
{ answers: { "1": "За", "2": "Проти" },   // ключ — індекс питання (питання 2 має індекс 1)
  source: "paper",                        // лише для голосів з обходу квартир
  enteredBy: "12",                        // хто вніс паперовий голос
  votedAt: ... }
```

Збори живуть у власній вкладці правління — «Збори»: форма створення,
активні збори, архів (і те, і те можна редагувати) та список протоколів.
Опитування лишилися на своїй вкладці й про збори нічого не знають.

Перше питання порядку денного однакове на всіх зборах, тому в формі
стоять не його формулювання, а поля «голова» й «секретар» (з підказкою
зі списку співвласників): рішення та «Слухали» для протоколу складаються
самі. Решта питань нумерується формою — номер вписувати не треба.

До кожного питання правління пише проєкт рішення (`agendaDecisions`) —
він друкується на листку опитування під питанням і потім лягає в протокол
рядком «Вирішили». Перед формуванням протоколу відкривається вікно, де
дописуються номер протоколу, голова й секретар зборів та «Слухали»
(`protocolNumber`, `chairName`, `secretaryName`, `agendaHeard`).

Голосування відкривається в час початку зборів (`votingOpensAt` — його
перевіряють і застосунок, і правила Firestore). До того мешканець бачить
порядок денний із проєктами рішень, але кнопки голосування ще немає:
голос до обговорення — це голос наосліп. Паперовий обхід правління може
вести й раніше — на нього обмеження не поширюється.

Листки опитування друкуються окремим комплектом на КОЖНЕ питання і,
якщо ввімкнено `sheetsByEntrance`, окремо на кожну парадну — саме так їх
роздають відповідальним особам. Внесення зібраних голосів іде тим самим
розрізом: спершу питання, потім парадна, далі окремий компактний рядок
кожного співвласника з вибором «За», «Проти» чи «Утримався».
Нові паперові голоси мають власні документи з `apt`, `ownerId`,
`source: 'paper'` та `answers`. ID власника береться з довідника, старі голоси
квартир читаються без міграції. Транзакції не перезаписують уже внесених
відповідей; позначки зберігаються при пошуку й переходах між питаннями.

На кожній сторінці листка повторюються питання, текст рішення та заголовки
колонок. Пункти рішення займають усю ширину листка: короткі переноси
всередині пункту об'єднуються, новий номер, маркер списку або порожній
рядок починає новий абзац. Нумерацію програма не додає. ПІБ і підпис
опитувача стоять тільки внизу кожної сторінки. ПІБ у формі
(`surveyors`) необов’язкове: порожнє поле залишає місце для ручного
заповнення, якщо підписи збирають різні люди.

Перше питання — обрання голови та секретаря — голосують з голосу на
очній частині зборів. Воно не входить до листків письмового опитування,
внесення паперових голосів та електронного бюлетеня. Номери інших питань
зберігаються: друк та відповіді починаються з питання 2 (ключ `answers[1]`).
У вікні **Сформувати протокол**, під питанням 1, правління вводить кількість
присутніх та голоси «За», «Проти», «Утримались». Ці числа зберігаються у
`chairVote: { present, yes, no, abstain }`. Усі значення — цілі невід’ємні,
присутніх має бути більше нуля, сума голосів не перевищує число присутніх.
Ті, хто не голосував, залишаються в знаменнику: рішення потребує понад
половину голосів присутніх. Площі у таблиці результатів першого питання
немає; його агреговані підсумки не приписуються власникам у поіменному
додатку. Старі відповіді `answers[0]` зберігаються, але не впливають на
результат очного обрання голови та секретаря.

Завершивши збори, правління кнопкою «Сформувати протокол» отримує
готовий PDF. Протокол лягає в Базу документів ОСББ (категорія
«Протоколи зборів») і йде розсилкою всьому будинку.

**Що попереду.** Електронний голос поки подається від квартири.
Паперовий голос уже фіксується окремо для кожного співвласника.
Коли зʼявиться електронний підпис, електронний голос теж зможе
подавати конкретний співвласник, який пройшов процедуру підпису.

**Як рахуються голоси.** За Статутом ОСББ кожний співвласник має один
голос незалежно від площі своїх приміщень, а рішення ухвалюється
більшістю від ЗАГАЛЬНОЇ кількості співвласників будинку, а не від тих,
хто взяв участь. Виняток — перше питання про обрання голови та секретаря:
його вирішує більшість присутніх, інакше збори не було б кому вести.
У результатах решти питань поруч із голосами показується площа.

Обидва документи повторюють ті, що ОСББ веде на папері, — структура,
шапки таблиць і формулювання збігаються з чинними зразками.

`pdfmake` вантажиться з CDN у мить першого натискання, а не в `<head>`:
разом зі шрифтами це близько двох мегабайтів, і мешканцям, які ніколи
не формують протоколів, вони не потрібні. Якщо cdnjs недоступний,
береться запасне джерело (jsDelivr).

## Розгортання Firebase

Правила Firestore і Storage, індекси та Cloud Functions описані в репозиторії
й розгортаються однією командою:

```bash
npm ci --prefix functions
firebase deploy --only firestore:rules,firestore:indexes,storage,functions
```

Завершення зборів і публікація протоколу працюють із панелі правління
через Firebase Auth і наявні правила Firestore. Оновлення цих дій
доставляється разом із застосунком через GitHub Pages; окремо публікувати
`finalizeMeeting` та `publishMeetingProtocol` для роботи застосунку не потрібно.
Доступ до запису підсумків, оголошень та документів має лише правління.

Перед підрахунком голосування закривається, потім застосунок читає
актуальні голоси й довідник без використання локального кешу.
Оголошення з підсумками та позначка `resultsSent` записуються однією
транзакцією. Протокол, оголошення з посиланням і позначка публікації
також записуються разом. Сталі ID сумісні з раніше опублікованими
серверними документами; повторна спроба оновлює їх і зберігає
дату створення та позначки прочитання.

Перше питання в усіх підсумках береться з `chairVote`. Перед складанням PDF
перевіряються внесені очні числа; перед публікацією — що текст і ці числа
не змінилися в іншій вкладці. Після збою введене лишається у зборах,
а публікацію можна повторити. Серверні функції у `functions/` залишаються
доступними для сумісності зі старими клієнтами.

### Вкладення загальних зборів і протоколів правління

Матеріали до зборів завантажуються у `polls/` (кожен файл менше 20 МБ).
Протоколи правління додаються через **База → Додати документ → Протоколи
зборів та правління**, у `osbb_docs/` (файл менше 30 МБ). Туди ж застосунок
завантажує сформовані PDF-протоколи загальних зборів. Підтримуються PDF,
Word та Excel, а в матеріалах зборів — також фото. Якщо браузер не визначив
тип файлу, він завантажується як `application/octet-stream`.

Правила дозволяють правлінню завантажувати, замінювати й видаляти файли;
авторизовані мешканці можуть їх читати. Доступ до Firestore-документів
зборів і Бази визначає `firestore.rules`, до самих файлів — `storage.rules`.

Помилка `storage/unauthorized` на шляху `polls/...` чи `osbb_docs/...`
означає, що Firebase Storage відхилив завантаження. Публікація коду
на GitHub Pages або лише `firestore.rules` не оновлює правила Storage.

Для проєкту `uspih-25` відкрийте **Firebase Console → Storage → Rules**,
переконайтеся, що вибрано бакет `uspih-25.firebasestorage.app`, вставте
повний вміст [storage.rules](storage.rules) і натисніть **Publish**.
Якщо консоль просить дозволити правилам Storage доступ до Firestore,
надайте цей дозвіл: функція `admin()` читає `apartments/{номер квартири}`.
У документі квартири облікового запису правління поле `isAdmin` має бути
логічним `true`, а не рядком.

Альтернатива для адміністратора з налаштованим Firebase CLI:

```bash
npx firebase login
npx firebase deploy --project uspih-25 --only storage
```

Якщо CLI запитає про IAM Role для cross-service rules, підтвердьте надання.
Не запускайте перше налаштування цього дозволу з `--non-interactive`:
CLI пропускає перевірку IAM у цьому режимі. Правила залишають завантаження
в `polls` та `osbb_docs` доступним лише правлінню.
Після публікації повторіть створення зборів із вкладенням або завантаження
протоколу правління в Базу.

### Одноразове налаштування Authentication

**Authentication → Settings**:

- **Password policy** — мінімум 8 символів, режим *Require enforcement*.
  Старі паролі продовжать працювати, нові короткі — ні.
- **User account management → Email enumeration protection** — увімкнути,
  щоб за відповіддю на вхід не можна було перебрати, які квартири
  зареєстровані.

Ці параметри задаються в консолі Firebase і не входять до статичних файлів
проєкту.

## Локальний запуск

ES-модулі не працюють через `file://`. Потрібен будь-який статичний сервер:

```bash
npm ci
python3 -m http.server 8000
```

Далі відкрити `http://localhost:8000`.

## Перевірки

```bash
npm run ci
npm test --prefix functions
```

Інтеграційні тести правил потребують Java 21 і Firebase Emulator Suite:

```bash
firebase emulators:exec --project uspih-25-rules-test --only firestore,storage "npm run test:rules"
```

## Оновлення кешу

У `index.html` посилання на файли мають параметр версії
(`style.css?v=110`, `style-chat.css?v=110`, `js/app.js?v=110`). Після зміни
коду збільште число разом із `VERSION` у `sw.js`. Команда `npm run check`
перевіряє узгодженість версій, імпортів та Firebase-конфігурації.

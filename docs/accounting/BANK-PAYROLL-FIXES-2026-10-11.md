# Исправления банка и зарплаты — 11 октября 2026

Объём: замечания E1–E10 и T8 из дополнительной проверки интеграции с
ПриватБанком. Изменения включены поверх `59ca01f`, с сохранением нового
интерфейса отчётности и версий XML-пакетов.

## Исправленное поведение

| Проверка | Результат |
|---|---|
| E1: смена токена | Исторические счета сохраняются для связей операций. Выписка загружается только по счетам, доступным новому токену. Недоступный счёт нельзя использовать для отправки. |
| E2: валюта зарплатного счёта | Зарплата отправляется с доступного текущего счёта в гривне. EUR и недоступные счета отклоняются до банковского запроса; остатки показываются в своей валюте. |
| E3: частичная загрузка | Отказ одного счёта не останавливает импорт остальных. Состояние и дата успешного импорта сохраняются отдельно по каждому счёту; интерфейс сообщает о частичном результате. Повтор не удваивает зачисления. |
| E4: конкурентное изменение назначения | Синхронизация обновляет банковские поля в транзакции и сохраняет актуальное назначение счёта, выбранное бухгалтером. Смена подключения проверяется по идентификатору подключения. |
| E5: сторно ранее импортированной операции | Если загруженная выписка содержит признак аннулирования того же REF, в открытом месяце снимаются разнос и подтверждение оплаты. Баланс квартиры, задолженность поставщику, зарплатное обязательство и журнал пересчитываются согласованно. |
| E6: отмена одновременно с продолжением ведомости | До удаления в банке резервируются платёж и ведомость. Параллельная отправка и повторная отмена блокируются. Подтверждённое удаление снимает только соответствующую строку из выполненной части плана. |
| E7: длинная история | Все платежи `sending`, `sent`, `unknown` загружаются отдельно от последних 200 записей истории. Старый незавершённый платёж остаётся доступным; виджет правления считает все ожидающие подписи платежи. |
| E8: совпадение ID человека с налогом | План использует отдельные пространства ключей `person` и `tax`; платежи сохраняют тип получателя. Сотрудник с ID `esv` учитывается по 661, а налог — по 651; сводки и отчёт различают их. |
| E9: соответствие утверждённому плану | Сервер проверяет сумму, получателя, вид, назначение, исходящий счёт и открытый месяц. Ключ обычной выплаты задаётся сервером: другой клиентский `proposalKey` не создаёт повторную выплату. |
| E10: возврат от запомненного плательщика | Признаки возврата проверяются до привязки к квартире. Возврат направляется на сверку и не увеличивает взносы жильца автоматически; несверенный возможный возврат блокирует экспорт отчёта. |
| T8: неизвестный флаг готовности | Импорт разрешён только при известной комбинации `WRK/N`. Отсутствующий или неизвестный `work_balance` не считается готовностью банка. |

## Неопределённые результаты и закрытые месяцы

При тайм-ауте удаления платёж получает `unknown`, а этап ведомости остаётся
незавершённым. Повторная отправка блокируется до проверки в Приват24.
Если процесс отмены оборвался, после десяти минут голова может подтвердить
наличие или отсутствие платежа и снять резервирование. Если выписка успела
подтвердить списание во время отмены, состояние `paid` сохраняется.

Сторно закрытого/закрывающегося месяца или операции с цепочкой возвратов
создаёт видимый конфликт и блокирует закрытие и экспорт отчётности. Закрытые
проводки сохраняются. Сторно обычной операции после открытия месяца
применяется повторной синхронизацией. Цепочки возвратов требуют отдельной
сверки; их автоматическое аннулирование не выполняется. Отменённую операцию
нельзя повторно разнести или выбрать как исходное списание для возврата.
Зарплатный платёж после сторно требует проверки в банке перед повтором.

## Совместимость сохранённых данных

Замороженные планы со старыми двухчастными ключами продолжают работать.
Отмена удаляет выполненный платёж по его ID, сохраняя остальные строки.
Старые платежи без `recipientType` распознаются по виду платежа, затем по
старому ключу. У старых настроек без `available` доступность уточняется при
первой проверке токена или синхронизации остатков.

Ранее ошибочно разнесённый возврат исправляется существующими действиями:
вернуть входящую операцию в очередь, затем связать её с исходным списанием
как возврат банка. Проверены очистка истории квартиры, восстановление
обязательства по зарплате и уменьшение выплаченного дохода в отчёте.
Автоматическая миграция финансовых записей рабочего проекта не выполнялась.

## Повторяемые проверки

Добавлены 19 серверных регрессионных сценариев на Firestore, 10 проверок
HTTP-адаптера и 2 проверки сводок зарплаты. Серверные сценарии используют
настоящие модули банка, зарплаты, платежей, проводок и отчётности. Проверка
длинной очереди исполняет загрузчик приложения с запросами к эмулятору.
Проверяются конкурентная отмена, прерванное удаление, повторная отправка,
старые планы, сторно взносов, зарплаты и оплаты поставщика, возвраты и
согласованность сумм со сводками и отчётом.

```sh
npm run ci
npm audit --omit=dev --audit-level=high --prefix functions
npx firebase emulators:exec --project uspih-25-rules-test --only firestore,storage "npm run test:rules"
```

Итог объединённой версии: **255/255** проверок расчётов и интерфейсной
логики, **148/148** серверных сценариев и проверок правил Firestore/Storage,
без пропусков — **403 проверки**. `npm run check` и сборка сайта прошли;
аудит серверных зависимостей сообщил `found 0 vulnerabilities`.

Банковские ответы имитировались. Реальные переводы, подписи КЭП и отправка
отчётности в ДПС не выполнялись. Переход ранее окончательного REF в сторно
остаётся проверкой устойчивости к такому ответу; соответствующий сценарий
реального банка требует обезличенной выписки.

## Доставка в приложение

Клиентские изменения доставляются существующим GitHub Pages workflow.
Серверные исправления должны быть опубликованы в Firebase. Существующий
workflow `Deploy Firebase` запускается после успешного `Quality checks`
для `main`, если настроен секрет `FIREBASE_SERVICE_ACCOUNT`.

Изменённый код используется функциями `bankAction`, `syncBank`,
`paymentAction`, `payrollAction`, `journalAction`, `reportsAction`,
а также действиями расходов и демо, вызывающими эти модули. Настроенный
workflow публикует весь набор функций. Правила и индексы не изменены.
Отсутствие ключа пропускает развёртывание; успешная проверка кода сама по
себе не подтверждает публикацию серверной части.
